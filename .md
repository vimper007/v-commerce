## E-Commerce Platform: Architectural Requirements Specification

### 1. Executive Overview & System Boundaries

This document defines the strict architectural requirements for a high-concurrency, distributed e-commerce platform. The system fundamentally splits UI delivery from backend transaction processing to eliminate event loop blocking under heavy traffic. The architecture enforces a strict physical network boundary between a Next.js frontend rendering engine and a decoupled Node.js backend cluster.

* **Next.js Frontend (The Delivery Layer):** Strictly responsible for UI orchestration, routing, Initial Page Load optimization (SSR/SSG), and edge-level request filtering. It will not handle heavy, long-running database transactions.
* **Node.js Backend (The Transaction Layer):** A decoupled, stateless API cluster responsible for secure financial transactions, webhook consumption, in-memory cart state, and concurrent row-locking operations.

### 2. Frontend Rendering & Caching (Next.js Layer)

The Next.js application must leverage hybrid rendering to maximize SEO indexing and minimize browser JavaScript payloads.

* **Product Catalog (Read-Heavy):** Product detail pages must utilize Incremental Static Regeneration (ISR). The build compiler will generate the static HTML shell at compile time and cache it at the edge.
* **Server Component Boundary:** Data fetching for the static catalog must occur exclusively within Server Components. All direct database access must be abstracted into a server-only Data Access Layer to enforce strict security boundaries and enable rate-limiting on expensive operations.
* **Client Component Boundary:** Interactive elements (e.g., Image Carousels, "Add to Cart" buttons) must be strictly isolated into leaf-level Client Components to prevent hydration errors and minimize the JavaScript bundle size.
* **Sequential Mutation Constraints:** The system will use Server Actions exclusively for localized, UI-driven mutations (e.g., standard form submissions) because they natively trigger Server Component re-renders and eliminate the need for manual client-state synchronization. Because Server Actions execute sequentially and only support POST requests, they must not be used for highly concurrent background jobs or read-heavy external APIs.
* **Search & Suspense:** URL-driven catalog search (reading `useSearchParams`) must be physically wrapped in `<Suspense>` boundaries. This guarantees the Next.js Node.js server does not crash during the static build by attempting to read a non-existent browser URL.

### 3. State & Authentication Bridge (The API Layer)

The system requires a strict data synchronization bridge between the Next.js delivery engine and the Node.js backend.

* **Stateless API Design:** The Node.js API must remain entirely stateless to allow for horizontal scaling across multiple container tasks during high-traffic events (e.g., flash sales).
* **In-Memory Cart State:** Shopping cart modifications must not hit a relational database directly. The Node.js backend will utilize Redis (an in-memory datastore) to achieve millisecond read/write speeds for active carts.
* **Decoupled Route Handlers:** For external API consumers and read-heavy public endpoints, the Next.js layer will expose standard Route Handlers to ensure full HTTP concurrency without being tied to the React rendering lifecycle.
* **Edge Middleware Authorization:** Next.js Edge Middleware will intercept incoming HTTP requests to verify JSON Web Tokens (JWTs). Unauthorized requests targeting secure checkout routes will be immediately redirected at the edge before the server spends CPU cycles rendering HTML.

### 4. High-Concurrency Transactions (Node.js Backend)

The backend must safely execute financial transactions without blocking the V8 engine event loop or creating race conditions.

* **Database Row Locking:** To prevent inventory overselling during high-concurrency checkouts, the Node.js API will execute strict SQL transactions (`SELECT ... FOR UPDATE`). This mathematically locks the specific database row to a single thread until the transaction completes or fails.
* **Webhook Consumption:** External payment gateway webhooks (e.g., Stripe) must strictly hit decoupled Next.js Route Handlers or the raw Node.js API. They must never use Server Actions, as webhooks require a decoupled HTTP-based execution model that supports full concurrency.
* **Message Queues (Event Loop Protection):** Upon receiving a bulk payment webhook, the Node.js API must not process heavy database updates on the main thread. It must instantly push the payload into a Message Queue (e.g., RabbitMQ or Redis Streams).
* **Worker Threads:** A dedicated pool of Node.js background worker threads will consume the Message Queue to perform the heavy database writes and trigger email receipts, ensuring the main server remains responsive to new HTTP requests.
